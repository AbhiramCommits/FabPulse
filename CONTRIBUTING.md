# Contributing to FabPulse

Thanks for helping improve FabPulse. This repository favours small, reviewable
commits, measured claims and tests that pin statistical behaviour.

## Setup

```bash
make setup     # Python virtualenv + backend deps + npm ci
make gen       # optional: regenerate the synthetic raw logs
make ingest    # load the warehouse
make ci        # full local gates
```

PostgreSQL is optional. Without it the backend probes for a server and falls
back to `data/fabpulse.db`. Never commit generated raw data, the local SQLite
warehouse, `.venv`, `node_modules` or `reports/` output by hand — reports are
regenerated by the exporter.

## Commit conventions

Use [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` a user-visible capability
- `fix:` a bug fix
- `test:` tests, fixtures, coverage or CI
- `chore:` scaffolding/tooling
- `docs:` README, ADRs, contributor docs
- `refactor:` behaviour-preserving code change
- `perf:` a measured performance change

Keep one logical change per commit. Describe the _why_ in the body when the
change is not obvious, and include before/after measurements for a `perf:`
commit. Do not squash unrelated steps; each commit should leave `make ci`
green.

## Branch and PR flow

1. Branch from `main`: `feat/<short-name>` or `fix/<short-name>`.
2. Make the change, add or update tests, run `make ci` and `make lint`.
3. Open a PR with: what changed, why, how it was verified, and any measured
   numbers. Link the relevant issue.
4. Keep the PR focused. Screenshots are required for visible UI changes.

## Review checklist

- [ ] API changes update `api/openapi.json` (`make snapshot`) and
      `web/src/api/types.ts`.
- [ ] New SQL lives in `fabpulse/queries.py`, not inline in routes.
- [ ] New statistics have a pure function with a known-array test.
- [ ] Every public Python function has a docstring; every exported TS function
      has a short comment.
- [ ] No secrets, credentials, raw data or local database files are committed.
- [ ] `make ci` passes, including the 85% coverage gate on `stats.py` and
      `ingest.py` and the frontend coverage thresholds.
- [ ] URLs remain shareable: any new filter is encoded by `useFilterState`.
- [ ] New dependencies are justified and pinned in `web/package-lock.json` /
      `api/requirements*.txt`.

## Code style

- **Python:** 3.11+, type hints, PEP 8, docstrings on public functions. SQL is
  Postgres-first and must also run on SQLite (no dialect-specific functions in
  the request path).
- **TypeScript/React:** functional components and hooks only, strict
  `tsc --noEmit`. ESLint (`npm run lint`) and Prettier (`npm run format`) are
  enforced. URL state belongs in `useFilterState`, not component-local state.
- **Charts:** all visual logic belongs in a pure `buildOption(data, theme)`
  function; the React wrapper stays thin so the option can be unit-tested.

## Adding an endpoint

1. Add a Pydantic response model in `api/fabpulse/models.py`.
2. Implement the query in `queries.py` and the statistics in `stats.py`.
3. Add the route in `main.py` using the shared `FilterDep`.
4. Add pytest coverage for the 200 shape, filter propagation and 400 paths.
5. Add a typed client method and, if needed, a data hook.
6. Run `make snapshot`, update `web/src/api/types.ts`, and run `make ci`.

## Reporting bugs

Include the filter URL, expected vs actual output, the browser/OS, and (for
backend issues) the database backend (`/api/health` reports it). For statistical
disputes, include the exact input series and expected UCL/LCL/run-rule output.
